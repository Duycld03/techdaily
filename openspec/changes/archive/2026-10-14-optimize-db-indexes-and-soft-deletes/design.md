# Design: Database Index Optimization & Soft-Delete Invariant Enforcement

## Context
See `proposal.md` for problem background and motivation.

DeepPace utilizes EF Core 9 with Npgsql on PostgreSQL 17 (pgvector). The system defines a global query filter `e => !e.IsDeleted` on all `BaseEntity` types. However, relational unique constraints were mapped as unconditional B-tree indexes, causing soft-deleted rows to occupy uniqueness slots and block re-creation. Additionally, `DocumentChunk` slice lookups lacked a composite index on `(DocumentBookId, ChunkOrder)`.

## Goals / Non-Goals

**Goals:**
- Enforce `HasFilter("\"IsDeleted\" = false")` on all unique business indexes across soft-deletable entities in `EntityConfigurations.cs`.
- Provide an $O(1)$ composite index for `DocumentChunk` on `(DocumentBookId, ChunkOrder)` with soft-delete filtering.
- Apply `.AsNoTracking()` on un-tracked queries in `GetTodayFocusHandler.cs`.
- Generate an idempotent EF Core migration that updates existing indexes without data loss or table locks.

**Non-Goals:**
- Modifying pgvector HNSW parameters or vector dimensions (768-D cosine remains untouched).
- Changing primary keys or entity relationship foreign key delete behaviors.
- Altering the global soft-delete query filter logic in `DeepPaceDbContext`.

## Decisions

### 1. Fluent API Configuration with Explicit Quoting
In `EntityConfigurations.cs`, all unique indexes on soft-deletable entities will be configured with `.HasFilter("\"IsDeleted\" = false")`:
```csharp
// Example for User.Email
builder.HasIndex(u => u.Email)
    .IsUnique()
    .HasFilter("\"IsDeleted\" = false");

// Example for DocumentChunk
builder.HasIndex(c => new { c.DocumentBookId, c.ChunkOrder })
    .IsUnique()
    .HasFilter("\"IsDeleted\" = false");
```
*Rationale*: Standard EF Core on PostgreSQL generates double-quoted column names in SQL (`"IsDeleted"`). Using escaped quotes in `HasFilter` ensures the index filter predicate matches the query filter predicate generated by EF Core, enabling the query planner to utilize the partial index automatically.

### 2. Composite Slice Index on DocumentChunk
Instead of relying on a standalone foreign key index on `DocumentBookId`, a composite unique partial index `(DocumentBookId, ChunkOrder)` will be added.
*Rationale*: `GetBookSlice` queries strictly by `DocumentBookId` and `ChunkOrder`. In PostgreSQL, B-tree composite indexing with equality on both columns provides immediate sub-millisecond seek performance.

### 3. Read-Only Query Tracker Optimization
In `GetTodayFocusHandler.cs`:
```csharp
var userPacersList = isAuthenticated
    ? await _dbContext.UserBookPacers
        .AsNoTracking()
        .Where(p => p.UserId == userId)
        .ToListAsync(cancellationToken)
    : new List<UserBookPacer>();
```
*Rationale*: These entities are read only to construct a dictionary map (`pacerMap`); change-tracking adds memory and garbage-collection overhead.

### 4. Migration Strategy
Create a single migration: `AddSoftDeletePartialIndexesAndSliceLookup`.
In PostgreSQL, replacing unconditional unique indexes with partial unique indexes drops the old unconstrained index and creates the partial index. This is non-breaking and does not lock tables during normal deployment.

## Risks / Trade-offs

- **Risk**: Database migration execution in existing environments.
  - *Mitigation*: Partial unique indexes are less restrictive than total unique indexes (they only enforce uniqueness among rows where `"IsDeleted" = false`). Any database that passed the previous total unique index will automatically satisfy the partial unique index without data collision.
- **Risk**: Query planner index matching.
  - *Mitigation*: The filter predicate `"IsDeleted" = false` exactly matches the EF Core global query filter applied in `DeepPaceDbContext`.
