# Design

## Context

See proposal.md — Why. Current state (verified via read-only inventory of all 12 endpoint files + `Program.cs`, 52 endpoints):

- OpenAPI is generated by built-in `AddOpenApi(...)` (`backend/src/TechDaily.Api/Program.cs:141-179`) with a single **document** transformer (Bearer scheme + global security). There are **no operation/schema transformers** and **zero `.Produces*` metadata** on any endpoint. Because delegates return non-generic `IResult` (via `Results.*` factories or `Result.Match(...)`), the generator infers only a bare `200` with no schema → Scalar shows "200 / No Body".
- `AddProblemDetails()` is registered (`Program.cs:41`) and `GlobalExceptionHandler` (`Middleware/GlobalExceptionHandler.cs`) emits RFC 7807 for unhandled 500s. Rate-limit rejection emits problem details. **Domain/validation errors, however, return ad-hoc anonymous JSON** (`Results.BadRequest(new { code = error.Code, error = error.Message })` / `Results.NotFound(...)`).
- `Result`/`Result<T>` (`Application/Common/Result.cs`) expose `IsSuccess`, `Value`, `Error`, `Match(...)`. `Error` (`Application/Common/Error.cs`) is a `record (string Code, string Message)` with canonical categories: `NotFound (RESOURCE_NOT_FOUND)`, `Unauthorized`, `Forbidden`, `Validation (VALIDATION_FAILED)`, `Conflict`, `ServerError`, plus domain-specific codes.
- Several groups return **inline anonymous objects** with no named DTO: Auth (register/login/google/refresh → `{ Token, User {…} }`), Notifications (vapid-key/subscribe/test), User (profile/update/change-password), System (ai-health), and `/health`.

## Goals / Non-Goals

**Goals**
- Every payload-returning endpoint declares a concrete, named success schema and its full producible status-code set in OpenAPI; documented codes equal emitted codes.
- Domain/validation errors are RFC 7807 `application/problem+json` carrying the domain `code`, so documented error schemas match real bodies.
- Correct REST status semantics for resource-creation endpoints (→ `201`).
- Curriculum roadmap operation copy is free of "30-day" framing.

**Non-Goals**
- No change to DTO field shapes/response data (only typing/metadata + status code + error envelope).
- No change to the curriculum computation logic or `CurriculumRoadmapResponse.TotalDays = 30` and the `% 30` / `/ 30` math (`Curriculum/.../GetCurriculumRoadmapHandler.cs`), nor to internal seeder/migration/handler slug `30-day-senior-curriculum`. Those are internal runtime/data concerns tracked separately; this change fixes doc-facing copy only.
- No change to authentication token/session flow beyond keeping its status code explicit (see D4).
- Not migrating to versioned/paginated envelopes.

## Decisions

### D1: Attach response metadata with explicit `.Produces*`, keep `IResult` delegates
Endpoints keep returning `IResult` via `Result.Match(...)`; we add fluent OpenAPI metadata to each route:
```
.Produces<TDto>(StatusCodes.Status200OK)              // or 201 / 202 / 204 (no body)
.ProducesProblem(StatusCodes.Status401Unauthorized)   // authenticated routes
.ProducesValidationProblem()                           // input-validating routes (400)
.ProducesProblem(StatusCodes.Status404NotFound)        // id-resolving routes
```
*Rationale*: `.Produces*` is explicit, greppable, and does not require rewriting every delegate into `TypedResults`/`Results<...>` union return types (invasive across 52 handlers). File-download endpoint (`GET /library/.../export-markdown`) uses `.Produces<FileContentResult>(200, "text/markdown")` semantics via `.Produces(200, contentType: "text/markdown")`.

### D2: Introduce named response DTOs for anonymous payloads
Add record DTOs in the owning feature namespaces so `.Produces<T>` can reference a named schema (fields mirror today's anonymous objects exactly):
- Auth: `AuthSessionResponse { string Token; AuthUserDto User }` (+ `AuthUserDto`) — reused by register/login/google/refresh.
- Notifications: `VapidPublicKeyResponse { string PublicKey }`, `PushAckResponse { bool Success }`, `PushTestResponse { bool Success; int Sent; int Total; int StalePurged }`.
- User: `UserProfileResponse { UserProfileDto User; ProfileStatsDto Stats }`, `UpdateUserProfileResponse {…}`, `MessageResponse { string Message }`.
- System: `AiHealthResponse {…}`; `/health`: `HealthStatusResponse { string Status; string Database; DateTime Timestamp }`.
Handlers/delegates return these instead of anonymous objects. No field renames.

### D3: Centralized RFC 7807 error mapping
Add `ResultHttpExtensions` (Api layer) converting a failed `Result`/`Result<T>` into problem details, replacing anonymous `{ code, error }`:
```
IResult ToProblem(this Error error, int statusCode) =>
    statusCode == 400
      ? Results.ValidationProblem(..., extensions: { ["code"] = error.Code })
      : Results.Problem(detail: error.Message, statusCode: statusCode,
                        title: <reason>, extensions: { ["code"] = error.Code });
```
Each endpoint passes the **same status code it already chooses today** (BadRequest→400, NotFound→404, Unauthorized→401), so this change standardizes the *body*, not the error status decisions. A `WellKnownErrorStatus` map (Error → status) is provided for endpoints that want category-driven mapping (`RESOURCE_NOT_FOUND`→404, `CONFLICT`/`AUTH_EMAIL_EXISTS`→409, `VALIDATION_FAILED`→400, `UNAUTHORIZED`→401, `FORBIDDEN`→403). The domain `code` is always preserved in `problem.extensions.code` so existing clients keying on `code` keep working.

### D4: Status-code corrections (create → 201)
| Endpoint | Now | Target | Note |
|---|---|---|---|
| `POST /api/v1/insights/generate` | 200 | **201** | persists `TechInsight`; add `Location: /api/v1/insights/{id}` if id available |
| `POST /api/v1/review/cards/from-highlight` | 200 | **201** | persists `SpacedRepetitionCard` |
| `POST /api/v1/review/cards/from-quiz-mistake` | 200 | **201** | persists `SpacedRepetitionCard` |
| `POST /api/v1/auth/register` | 200 | **200 (unchanged)** | see decision below |

Already-correct (only add metadata, no code change): `library/import` (201), `notes/highlights` POST (201), `upload-pdf`/`import-remote-pdf` (202), all `DELETE` + `auth/revoke` + `push/unsubscribe` (204).

**Auth register stays `200`**: register/login/google/refresh share one `{ Token, User }` session payload and the frontend auth store treats them uniformly. They return a session token, not a REST resource addressable at a `Location`; forcing `201` would be inconsistent within the auth family and would break the frontend's `200` expectation. This is the conservative choice; flagged here for reviewer override — if the reviewer wants strict resource semantics, register→201 can be added as a one-line change plus a frontend auth-store update.

### D5: Copy fix — doc-facing only
Edit `CurriculumEndpoints.cs:34` `.WithDescription(...)` to drop "30-day" (e.g. "Retrieves the Senior Engineering Craft Handbook roadmap grouped into 4 core technical pillars with authenticated user progress."). Internal 30-based logic, seeder slug, migration SQL, and test method names are out of scope (Non-Goals).

## Risks / Trade-offs

- **HTTP contract change (201/204)**: clients asserting `200` on the three create endpoints break. *Mitigation*: update the frontend callers + regenerate `frontend/types/api.generated.ts` (`npm run gen:api`); the created-resource body is unchanged, only the status line moves 200→201.
- **Error body shape change (`{code,error}` → problem+json)**: `frontend` error handling (`useApiClient`) may read `.error`/`.code` off the body. *Mitigation*: problem details keeps the domain `code` in `extensions.code`; audit and update the client's error parser as a task. RFC 7807 aligns with the project's existing `AddProblemDetails`/`GlobalExceptionHandler` convention.
- **Metadata drift**: `.Produces` is manual and can diverge from actual returns. *Mitigation*: the parity scenario is verified against the live `/openapi/v1.json` plus a runtime smoke of a create endpoint; keep declarations adjacent to each route.
